# 05 项目复盘

## 目标与完成情况

本次选择企业知识问答 Agent，目标不是仅将检索内容拼接给 LLM，而是实现“模型选择动作 → 工具执行 → 观察结果 → 模型决定后续动作或结束”的可追踪循环。在考试规定的范围内，用 CLI、合成制度、文档检索与读取工具、步数上限、离线 Mock 和真实模型接入完成原型。

已观察到七次真实模型运行，覆盖六类验收场景：正常问答、相互冲突的文档、资料外问题、相似问题改写、上下文追问、工具失败（检索失败和读取失败分别测试）。完整操作证据应保存为 `examples/live_*_trace.json` 并由 `03-evaluation.md` 引用。此前生成的离线测试曾得到 9 项通过；最终提交前仍需在本机重新执行 pytest 并以实际输出为准。

## 最难问题及解决思路

**1. 冲突文档不能用版本日期猜答案。** D01 规定报销期限 30 天，D02 规定 15 天，但两个文件都没有说明适用部门及版本优先级。实际模型先搜索，再分别读取原文，最后说明冲突并提示需要确认，而没有自行认定新版本覆盖旧版本。这使“有依据地不回答唯一结论”成为明确的产品行为。当前 `knowledge_gap` 仍需改进：冲突场景返回了 `null`，建议将缺少适用范围和优先级写入结构化字段。

**2. 工具调用成功不等于证据可靠。** 在股票期权问题中，轻量检索曾返回报销制度 D01、D02 这样的无关候选。模型最终没有编造答案，说明回答侧有一定的保守性；但检索误召回会占用步骤并增加错误风险。后续应加入最低相关性阈值、关键词/语义混合检索与文档重排序；同时要检查回答是否真正被已读取原文支持，而非仅验证引用字符串存在。

**3. Agent 必须能观察错误后改变行为。** 检索失败时，模型尝试再次搜索；读取失败时，模型尝试重新读取 D03；连续失败后均返回资料不足、没有假装工具成功。这里的故障注入是持续失败，已经证明基本失败兜底，**尚未验证“一次失败后恢复”的续跑能力**。此外，资料外问题的第二次搜索基本重复第一次关键词，说明还需要加入查询去重与有效改写检查，避免无效重试。

## 学习与取舍

Agent 和固定流程 RAG 的区别在于，工具结果能影响模型的下一步选择。为符合考试对真实决策的要求，保留了 LiveModel 模式及逐步 Trace，而不是仅用预设规则模拟决策。另一方面，没有额外开发 Web UI、复杂多 Agent 架构或生产部署，优先确保可运行性、引用追踪、边界处理和测试证据。

离线 Mock 测试利于快速、可重复地检查控制流；真实模型测试能展示模型基于结果选择动作，但输出具有非确定性，需要保存实际 Trace、重复测试并避免过度概括。系统还设置最大步骤限制，防止持续调用工具而无法结束。

## 已知限制和下一步

1. 检索目前是轻量基线，资料外问题存在误召回；可增强为混合检索并加入相关性门槛。
2. 对制度冲突仍依赖模型是否找到并读取所有相关文档；可强制核查同主题不同版本，并增加版本适用范围字段。
3. 当前引用校验不能等同于完整语义蕴含验证；可加入回答-证据一致性检查及更明确的 `knowledge_gap`。
4. 需要补充“故障一次后恢复”、超时、重试退避、查询去重、同一问题多次运行的稳定性测试。
5. 未接入真实企业数据、用户权限、审计日志与生产监控；目前仅为考试级合成数据原型。
